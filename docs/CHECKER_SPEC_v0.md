# 設計方針書 — 形式検証チェッカー MCP v0

このファイルは Claude Code に渡す設計指示書です。リポジトリ直下に `CLAUDE.md` として置くことを想定しています。

---

## 0. このプロジェクトが作るもの

**一行を受け取り、真偽を返す検証器。** それ以上でもそれ以下でもありません。

チューターではありません。学習プラットフォームでもありません。エージェント（Claude Code を含む）や人間が生成した式・証明の一行を受け取り、Lean4 で判定して結果を返す、単機能の MCP サーバです。

---

## 1. 絶対に守る原則

### 1.1 判定経路に LLM を入れない

これがこのプロジェクトの存在理由です。判定は決定的でなければなりません。

- Lean4 / 既存の検証資産のみが判定を下す
- LLM は前処理（自然言語→形式表現の変換候補生成）にのみ使ってよいが、**その出力は必ず検証器を通す**
- 「たぶん正しい」を返す経路を一切作らない

### 1.2 判定できないときは、判定できないと返す

出力は必ず三値のいずれか。例外を投げて終わらない。

| 値 | 意味 |
|---|---|
| `VALID` | 検証器が真であることを確認した |
| `INVALID` | 検証器が偽であることを確認した |
| `UNDECIDED` | 検証器が判定を下せなかった |

`UNDECIDED` はエラーではなく、**正当な戻り値**です。タイムアウト、構文非対応、公理不足、深さ制限——すべて `UNDECIDED` + 理由コードとして返します。

理由コード（初期セット、必要に応じ追加）:
`TIMEOUT` / `PARSE_FAILURE` / `UNSUPPORTED_SYNTAX` / `MISSING_AXIOM` / `DEPTH_LIMIT` / `OUT_OF_SCOPE`

### 1.3 D-FUMT₈ を API 表面に出さない

内部で 8 値論理を使うのは自由ですが、**v0 の外部インタフェースは上記三値のみ**とします。

理由: 利用者が D-FUMT₈ を理解しなければ使えない設計にすると、誰も使いません。まず使われること。理論の説明はドキュメントで、API では要求しない。

（`NEITHER` を含む内部表現は保持し、将来 `verbose` オプションで開示できるようにしておく。）

## 2. v0 のスコープ

### 作るもの

MCP サーバ 1 本。ツールは **2 つだけ**。

```
verify(expression: str, context?: str, timeout_ms?: int)
  -> { verdict: VALID|INVALID|UNDECIDED,
       reason_code?: str,
       detail?: str,
       elapsed_ms: int,
       checker_version: str }

stats()
  -> { total: int, valid: int, invalid: int, undecided: int,
       decision_rate: float,
       reason_breakdown: { <code>: int } }
```

### 作らないもの（v0 では明示的に非目標）

- UI / Web フロントエンド
- ユーザー登録・認証・課金
- ゲーミフィケーション、進捗管理、学習履歴
- 自然言語での対話・解説生成
- 複数バックエンド対応（Lean4 のみ）
- Claude 固有の機能への依存

非目標を実装しようとした場合、**手を止めて確認を取ること。**

---

## 3. 唯一の指標

```
decision_rate = (VALID + INVALID) / total
```

**判定率。** 投入された式のうち、何割に判定を返せたか。

- `stats()` は常にこの数字を返す
- ログには全リクエストを記録し、この数字を毎日算出できる状態を保つ
- 利用者数・スター数・DL数は指標にしない

v0 の成功条件は「判定率が高いこと」ではありません。**判定率が測れる状態になること**です。初期値が 0.1 でも構いません。

---

## 4. 反証台帳

`UNDECIDED` は捨てない。すべて記録する。

記録項目: 入力式（正規化後）、理由コード、タイムスタンプ、checker_version、経過時間。

- 個人情報・利用者識別子は記録しない
- 保存形式は追記専用（JSONL 推奨）
- これが次に実装すべき機能を決める唯一の根拠になる

`UNSUPPORTED_SYNTAX` が集中した構文が、次のスプリントの対象です。推測で機能を足さない。

---

## 5. プロトコル方針

- **MCP 仕様に対して実装する。** Claude Desktop / claude.ai 固有の挙動に依存しない
- stdio と HTTP/SSE の両トランスポートを想定。v0 は stdio のみ実装可、ただし I/O 層を分離しておく
- ツール分類は「checker」（判定して真偽を返す）。「harness」機能は混ぜない
- ライセンス AGPL-3.0（既存リポジトリに合わせる）

---

## 6. 実装順序

1. Lean4 を叩いて真偽を返す最小の関数（MCP なし、CLI で動くこと）
2. 三値 + 理由コードの戻り値スキーマを固定
3. 反証台帳への追記
4. `stats()` の算出
5. MCP サーバとして包む
6. README（**D-FUMT₈ を知らない人が 5 分で動かせること**）

各段階で動くものを残す。5 まで到達しないうちに 6 の体裁を整えない。

---

## 7. 品質基準

- タイムアウトは必ず効く。ハングしたら `UNDECIDED/TIMEOUT`
- 不正な入力でクラッシュしない。`UNDECIDED/PARSE_FAILURE`
- `checker_version` を全レスポンスに含める（過去の判定の再現性のため）
- 判定ロジックにテストを書く。特に **`UNDECIDED` を返すべきケースのテスト**を優先する

---

## 8. 判断に迷ったとき

- 機能を足すか迷ったら、足さない
- 「たぶん正しい」を返すか迷ったら、`UNDECIDED` を返す
- 理論を API に出すか迷ったら、出さない
- 急がず、ゆっくりと。

# Phase 2 以降（v0 完了までは着手しない）

以下は将来の設計方針であり、**v0 のスコープ外**です。`decision_rate` が算出できる状態になるまで、このセクションの実装に着手しないこと。ただし v0 の設計時に、ここへの拡張余地だけは潰さないようにする。

構成は三層。

```
第1層  checker    verify / stats                      ← v0
第2層  education  locate_first_error / boundary_report / escalate
第3層  harness    calibration / regression / transfer
```

**実装順序は 第1層 → 第3層② → 第2層。** 第2層より先に較正ハーネス（3.2）を作ります。理由は 3.2 に記載。

---

## 9. 第3層-② 較正ハーネス（Phase 2 の本命）

### 9.1 目的

LLM の出力を検証器にかけ、**「確信度」と「正当性」の乖離を測定する**。

正答率を測る装置は世に多数あるが、**「誤りを断定的に述べる率」を測る標準はまだ存在しない**。ここが空白。

### 9.2 なぜこれを第2層より先に置くか

- チェッカーが未完成でも成立する。`decision_rate` が 0.2 でも、判定できた範囲での過信率は測れる
- 学習者コホートへのアクセスが不要。一人で完結する
- そのまま論文になる
- 教育向け・コード検証向けの両方に同じ計器が使える

### 9.3 測定する指標

```
overconfidence_rate  = (断定的 ∧ INVALID) / 断定的な出力の総数
silent_failure_rate  = (INVALID ∧ 留保表現なし) / 全出力
abstention_accuracy  = (留保した ∧ 実際に UNDECIDED または INVALID) / 留保した総数
decisive_correct_rate = (断定的 ∧ VALID) / 断定的な出力の総数
```

主要指標は **`overconfidence_rate`**。低いほどよい。

### 9.4 断定／留保の判定方法

ここが実装上の最大の注意点。

- **断定・留保のラベル付けに LLM を使わない。** 判定経路に LLM を入れない原則（1.1）は、この計器にも適用される
- 対象 LLM に**構造化出力を要求する**：`{ answer, confidence: DECISIVE|HEDGED|ABSTAIN }`
- 自己申告の confidence をそのまま使い、文章表現からの推定はしない
- 自己申告が取れないモデルは、**測定対象外**として除外する（推定して無理に含めない）

### 9.5 データセット

- 検証器が `VALID`/`INVALID` を返せる問題のみを対象にする
- `UNDECIDED` になった問題は測定から除外し、除外率を必ず併記する
- 除外率が高いこと自体は失敗ではない。**隠さないことが要件**

### 9.6 出力

```
calibrate(model_id, dataset_id)
  -> { n_total, n_excluded, exclusion_rate,
       overconfidence_rate, silent_failure_rate,
       abstention_accuracy, decisive_correct_rate,
       checker_version, dataset_version, timestamp }
```

全レコードを台帳に保存。過信が出た事例は、入力・出力・判定をそのまま残す。

### 9.7 やらないこと

- モデルのランキング表を作らない（測定器であって順位表ではない）
- スコアを一つの数値に合成しない
- 「このモデルは安全」といった評価を返さない

---

## 10. 第3層-① 回帰ハーネス

baseline セッションと現行を比較し、劣化を検出する。

```
regression(baseline_id, current_id)
  -> { decision_rate_delta, reason_code_deltas, regressions[] }
```

- 既存の `regression_check` の設計思想を踏襲
- `decision_rate` が下がった、または特定の理由コードが増えた場合に検出
- CI に組み込めること

---

## 11. 第3層-③ 転移ハーネス（設計のみ・実装しない）

AI 支援ありの学習と、支援なしでの定着の差を測る。

**最重要だが、単独では成立しない。** 学習者コホートへのアクセスが必要なため、9 の較正ハーネスで計器としての信用を作ったのち、研究機関と協働する形でのみ実装可能。

v0/Phase 2 では**インタフェース設計のみ**を残し、実装しない。

---

## 12. 第2層 教育向けツール（Phase 3）

チェッカーの上に被せる**薄い層**。第2層のツールは、いずれも第1層を呼ぶだけで、独自の判定ロジックを持たない。

### 12.1 `locate_first_error(steps[])`

複数行の解答を受け取り、**最初に破綻した行番号だけ**を返す。

```
-> { first_error_index: int | null, verdict_per_step: [VALID|INVALID|UNDECIDED] }
```

**やらないこと（重要）:**
- 誤りの説明を生成しない
- 訂正案を出さない
- 代替解法を提示しない

説明を生成した瞬間に、保証できない領域に踏み込む。説明は人間の管轄。

### 12.2 `boundary_report(topic)`

その単元について、検証器が**判定できる範囲とできない範囲**を列挙する。

```
-> { supported: [...], unsupported: [...], known_gaps: [...],
     source: "ledger", ledger_window: "..." }
```

- 反証台帳の実データから生成する。手書きのリストにしない
- 教師が授業前に「AI が何を保証できないか」を把握するためのもの

### 12.3 `escalate(expression, reason_code)`

`UNDECIDED` を人間のキューに積む。

```
-> { ticket_id, queued_at, reason_code }
```

機械が判定を降りた地点が、そのまま人間の管轄になる。**この境界を可視化することが目的**であり、キューを短くすることは目的ではない。

---

## 13. Phase 2 以降で守る原則（再掲・追加）

1. **判定経路に LLM を入れない。** 較正ハーネスのラベル付けにも適用する（9.4）
2. **除外したものを隠さない。** `exclusion_rate` を常に併記する
3. **説明を生成しない。** 第2層は位置を返すのみ
4. **順位表を作らない。** 計器であって審判ではない
5. 第2層より先に第3層② を作る
6. 急がず、ゆっくりと。
